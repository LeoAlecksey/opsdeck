# Как подключить облако к десктопному приложению и не хранить ничьи ключи

Я пишу OpsDeck — открытое десктопное приложение, в котором DevOps-инженер держит в одном окне терминал, Kubernetes, SSH-хосты, базы, логи и всё остальное, по чему обычно разложены пять вкладок и три консоли. В версии 0.8.0 там появился раздел Yandex Cloud, и, пока я его делал, вылезла пачка вещей, про которые в документации не пишут, потому что они начинаются ровно там, где документация заканчивается.

Главный вопрос был не «как позвать API», а «как не стать хранилищем чужих ключей». Про это и статья: сначала рассуждение, потом код и четыре конкретные грабли, на каждую из которых я наступил лично.

## Задача

Инженер открывает приложение и хочет увидеть свои виртуалки: что работает, что остановлено, за что капает. Плюс сети, группы безопасности, адреса, выданные доступы и остаток на счету. Остановить машину, запустить, зайти по SSH в один клик.

Технически вариантов три.

**Вариант первый: попросить токен.** Поле «вставьте OAuth-токен», сохранили, ходим в API. Так делают очень многие.

**Вариант второй: OAuth-флоу.** Приложение открывает браузер, получает код, меняет на токен, обновляет по refresh. Красиво, но требует зарегистрированного приложения, своего redirect-URI и, по-хорошему, серверной части.

**Вариант третий: работать профилями CLI пользователя.** У человека уже установлен `yc`, уже сделан `yc init`, уже лежит профиль с авторизацией. Приложение ничего не спрашивает и ничего не хранит — оно просто вызывает ту же CLI, что человек вызывает руками.

Я выбрал третий. Ниже — почему, и во что это обошлось.

## Почему не токен

Десктопное приложение — плохое место для секрета, и вот честный список причин, а не абзац про «безопасность — наш приоритет».

**Хранить негде.** В вебе есть сервер, в десктопе — файл в домашней папке. Да, есть системные хранилища: Keychain на macOS, DPAPI на Windows, Secret Service в Linux. Последнее — это «если установлен gnome-keyring или kwallet, если сессия разблокирована, если D-Bus на месте». На типичном рабочем Linux-ноутбуке DevOps-инженера это «если» срабатывает не всегда, а запасной путь в таких схемах — почти всегда файл рядом с конфигом.

**Секрет утекает мимо хранилища.** Конфиг попадает в бэкап. Папка синхронизируется в облако. Человек делает скриншот окна с настройками и несёт в issue. Присылает лог — а там в одной строке команда целиком. Я этого насмотрелся: в репозитории есть отдельный скрипт, который проверяет, что в чужих pull request'ах не подменили ссылки, и отдельное правило — никогда не печатать в лог ничего похожего на ключ. Но лучшая защита от утечки секрета — его отсутствие.

**Права получаются шире нужного.** Токен — это весь аккаунт. Пользователь хотел показать приложению список виртуалок в одном каталоге, а дал доступ ко всему, до чего дотягивается сам. Сервисный аккаунт с узкой ролью — правильный ответ, но это отдельная настройка, которую в реальности сделают единицы.

**Ответственность.** В тот момент, когда приложение сохранило чужой токен, оно стало объектом, к которому применимы вопросы «а как вы его шифруете», «а что при компрометации», «а можно политику хранения». Для проекта, который пишет один человек по вечерам, это не та ответственность, которую стоит брать добровольно.

А профиль `yc` всё это снимает разом. Авторизация уже есть, её жизненным циклом управляет сам пользователь и официальная CLI. Права — ровно те, что у человека. Отозвать доступ — `yc config profile delete`. Приложение не участвует.

Побочный, но приятный эффект: ровно такой же подход у меня уже был для Kubernetes (`kubectl` и kubeconfig пользователя) и для git. Пользователь получает одинаковое поведение во всех разделах: приложение — это удобный способ запустить то, что у тебя и так есть.

Минусы тоже назову, чтобы не было рекламы. Нужна установленная CLI. Нужно переживать разброс её версий. И каждый вызов — это запуск процесса, то есть десятки миллисекунд накладных расходов и никакого стриминга. Для интерфейса, который обновляется по кнопке, это неважно; для чего-то реалтаймового так делать не надо.

## Как это выглядит в коде

Всё общение — один маленький слой. CLI умеет `--format json`, и это ровно то, что нужно:

```rust
/// `yc` с аргументами; stdout как есть (для `--format json` — JSON).
fn yc(args: &[&str]) -> Result<String, String> {
    let mut cmd = Command::new(yc_bin());
    cmd.args(args).stdin(Stdio::null()).stdout(Stdio::piped()).stderr(Stdio::piped());
    process::no_console(&mut cmd);
    let out = cmd.output().map_err(|e| {
        if e.kind() == std::io::ErrorKind::NotFound {
            "yc не найден — установите Yandex Cloud CLI и выполните «yc init» или укажите путь к файлу кнопкой ниже".to_string()
        } else {
            format!("не удалось запустить yc: {e}")
        }
    })?;
    if !out.status.success() {
        return Err(explain(&String::from_utf8_lossy(&out.stderr)));
    }
    Ok(String::from_utf8_lossy(&out.stdout).into_owned())
}

fn yc_json(args: &[&str]) -> Result<Value, String> {
    let mut a = vec!["--format", "json"];
    a.extend_from_slice(args);
    let text = yc(&a)?;
    if text.trim().is_empty() {
        return Ok(Value::Array(vec![]));
    }
    serde_json::from_str(&text).map_err(|e| format!("yc вернул не JSON: {e}"))
}
```

Три вещи здесь сделаны нарочно.

`Command::new` вызывает файл напрямую — **никакого `sh -c`**. Как только появляется шелл, появляется и разбор строки, и вместе с ним кавычки, подстановки, `$(…)` и весь зоопарк. Аргументы передаются массивом, и строка команды нигде не собирается.

`stdin(Stdio::null())` — чтобы CLI, если ей вдруг захочется что-то спросить, не висела молча, ожидая ввод, которого в GUI не будет никогда.

И идентификаторы проверяются до вызова:

```rust
/// Идентификаторы и имена в Yandex Cloud: буквы, цифры, дефис, подчёркивание и точка.
/// Всё остальное в аргументы CLI не пускаем.
fn valid(id: &str) -> bool {
    !id.is_empty() && id.len() <= 200 && !id.starts_with('-')
        && id.chars().all(|c| c.is_ascii_alphanumeric() || matches!(c, '-' | '_' | '.'))
}
```

Отдельно обращу внимание на `!id.starts_with('-')`. Шелла нет, инъекции команд нет — но значение, начинающееся с дефиса, CLI прочитает как **флаг**, а не как значение. Это тот класс дыр, который переживает переход на «безопасный» запуск без шелла, и про него регулярно забывают.

Поверх этого — полтора десятка команд Tauri: `yc_status`, `yc_clouds`, `yc_folders`, `yc_instances`, `yc_instance_op`, `yc_networks`, `yc_subnets`, `yc_sec_groups`, `yc_addresses`, `yc_service_accounts`, `yc_bindings`, `yc_billing`. Каждая — вызов CLI и чистая функция-парсер к ответу. Запомните это разделение, в конце оно сыграет.

## Грабля №1: приложение из меню не видит ваш PATH

Первый же отзыв после сборки: «в консоли `yc config list` работает, а приложение пишет, что yc не найден».

Это не про Yandex Cloud, это общая беда десктопных приложений, и объясняется она просто. Когда вы запускаете программу из терминала, она наследует окружение шелла — а шелл прочитал `~/.bashrc` или `~/.zshrc`, куда установщики любят дописывать свои пути. Когда вы запускаете ту же программу из меню приложений, ярлыком или из Dock, её окружение приходит от systemd user session (Linux) или launchd (macOS). Эти файлы там никто не читал. PATH — голый.

А официальный установщик `yc` кладёт бинарник в `~/yandex-cloud/bin` и дописывает PATH именно в `~/.bashrc`. Идеальное совпадение: в терминале всё есть, в приложении ничего нет.

Лечится в три слоя.

**Слой первый — спросить PATH у login-шелла.** Один раз при старте, с маркером вокруг значения и жёстким таймаутом, потому что чужой `.zshrc` может делать что угодно, вплоть до бесконечного ожидания:

```rust
let shell = std::env::var("SHELL").unwrap_or_else(|_| "/bin/zsh".into());
let marker = "__OPSDECK_PATH__";
let mut child = Command::new(&shell)
    .args(["-l", "-c", &format!("printf '{marker}%s{marker}' \"$PATH\"")])
    .stdin(Stdio::null())
    .stdout(Stdio::piped())
    .stderr(Stdio::null())
    .spawn()
    .ok()?;
let deadline = Instant::now() + Duration::from_millis(1500);
// …ждём до дедлайна, иначе kill
out.split(marker).nth(1).map(str::to_string)
```

Маркеры нужны потому, что профиль пользователя может напечатать в stdout что угодно — приветствие, вывод `neofetch`, предупреждение менеджера версий. Берём то, что между маркерами, остальное выбрасываем. Полторы секунды — верхняя граница, после которой мы просто живём без этого PATH: лучше не найти CLI, чем не показать окно.

**Слой второй — знать привычные места.** Если в PATH не нашлось, смотрим туда, куда кладут установщики:

```rust
fn yc_candidates(home: &Path, windows: bool) -> Vec<PathBuf> {
    let name = if windows { "yc.exe" } else { "yc" };
    let mut out: Vec<PathBuf> = ["yandex-cloud/bin", ".local/bin", "bin", ".yandex-cloud/bin"]
        .iter().map(|d| home.join(d).join(name)).collect();
    if windows {
        out.push(home.join("AppData/Local/Programs/Yandex.Cloud/bin").join(name));
    } else {
        out.extend(["/usr/local/bin", "/usr/bin", "/opt/yandex-cloud/bin", "/snap/bin"]
            .iter().map(|d| Path::new(d).join(name)));
    }
    out
}

/// Чем запускать: сохранённый путь, затем PATH, затем привычные места установки.
fn yc_bin() -> PathBuf { /* saved → PATH → candidates → просто "yc" */ }
```

**Слой третий — дать указать путь руками.** Потому что первые два слоя всё равно кого-нибудь не покроют. Кнопка в интерфейсе, а в бэкенде — проверка, что это вообще та программа:

```rust
let out = Command::new(&p).arg("version") /* … */ .output()?;
if !out.status.success() {
    return Err(format!("{} не отвечает на «version»", p.display()));
}
```

И текст рядом с кнопкой, объясняющий причину, а не просто «укажите путь»: «Приложение, запущенное из меню, не читает ~/.bashrc, куда установщик дописывает PATH». Человек должен понимать, почему его просят это сделать, иначе он решит, что приложение сломано.

## Грабля №2: у разных версий CLI разные команды

Раздел «Счёт» я сделал через `yc billing account list`. У меня работало. У пользователя с CLI 1.41 — `Unknown command "billing"`.

Команда за время жизни CLI называлась по-разному, а в какой-то момент из публичной CLI пропала. Классический случай, когда продукт быстро развивается и приложения-обёртки оказываются между версиями.

Соблазн — показать текст ошибки CLI. Так делать не надо: пользователь видит `Unknown command` и уверен, что сломалось **ваше** приложение. Правильно — распознать этот конкретный случай и объяснить по-человечески:

```rust
/// Ответ CLI «такой команды нет»: в 1.41 платёжных аккаунтов в `yc billing` уже (или ещё) нет.
fn unknown_command(text: &str) -> bool {
    let t = text.to_lowercase();
    t.contains("unknown command") || t.contains("unknown group") || t.contains("неизвестная команда")
}

pub async fn yc_billing() -> Result<Billing, String> {
    // в разных версиях CLI команда называлась по-разному, а в 1.41 её нет совсем
    for args in [["billing", "account", "list"], ["billing", "accounts", "list"]] {
        match yc_json(&args) {
            Ok(v) => return Ok(Billing { supported: true, accounts: parse_billing(&v) }),
            Err(e) if unknown_command(&e) => continue,
            Err(e) => return Err(e),
        }
    }
    Ok(Billing::default()) // supported: false
}
```

Обратите внимание на тип ответа: не `Vec<Account>`, а структура с флагом `supported`. «Нет данных» и «эта CLI так не умеет» — разные состояния, и в интерфейсе они выглядят по-разному. Во втором случае раздел пишет, что установленная CLI не умеет показывать платёжные аккаунты, и даёт кнопку, открывающую консоль в браузере. Ноль на экране вместо остатка на счету — куда хуже, чем честная надпись.

Общее правило, которое я вывел: **stderr чужой CLI — это не сообщение для пользователя**. Поверх него нужен переводчик:

```rust
fn explain(stderr: &str) -> String {
    let line = stderr.lines().map(str::trim).find(|l| !l.is_empty()).unwrap_or("yc не ответил");
    if line.contains("Not authenticated") || line.contains("token has expired") || line.contains("OAuth") {
        return "нет входа в Yandex Cloud — выполните «yc init» (или «yc config set token …») в терминале".into();
    }
    if line.contains("PermissionDenied") || line.contains("Permission denied") {
        return "нет прав на эту операцию у текущего профиля yc".into();
    }
    if line.contains("NotFound") {
        return "объект не найден — возможно, выбрано другое облако или каталог".into();
    }
    line.chars().take(300).collect()
}
```

Последняя строка важна не меньше остальных: то, что не распознали, показываем как есть, обрезав до трёхсот символов. Никаких «произошла ошибка».

## Грабля №3: схема ответа шире, чем кажется

Раздел «Адреса» у меня показывал часть строк с пустым адресом. Я читал `external_ipv4_address` — а у внутренних адресов поле называется `internal_ipv4_address`, и зоны у них нет, есть подсеть.

```rust
let ext = x.get("external_ipv4_address");
let int = x.get("internal_ipv4_address");
let src = ext.or(int);
Address {
    address: src.map(|e| str_of(e, "address")).unwrap_or_default(),
    external: ext.is_some(),
    zone: ext.map(|e| str_of(e, "zone_id"))
        .unwrap_or_else(|| int.map(|e| str_of(e, "subnet_id")).unwrap_or_default()),
    // …
}
```

Вывод банальный, но проверенный болью: **пишите парсер по реальному JSON, а не по странице документации**, и прогоняйте его на своём настоящем каталоге, где есть всё — и внутренние адреса, и прерываемые машины, и остановленные.

Заодно я добавил в этот раздел то, за что меня потом благодарили: зарезервированный, но ни к чему не привязанный внешний адрес помечается как «нет (платный простой)». Деньги за него идут, а пользы ноль. Интеграция с облаком полезна ровно в тот момент, когда она показывает не то, что лежит в API, а то, что человеку важно: что не работает и за что он платит зря. По той же причине конфигурация машины выводится строкой `standard-v3 · 2 vCPU (20%) · 4.0 GB · прерываемая` — доля ядра и прерываемость влияют на счёт сильнее, чем всё остальное.

## Грабля №4: кнопка, которая останавливает настоящую машину

Чтение данных — это полдела, инженер хочет ещё и жать кнопки. Тут действует правило, которое я держу во всём приложении: **изменяющая операция — только по явному нажатию и только с вопросом**, в котором написано, что именно произойдёт.

Диалог перед остановкой говорит прямым текстом, что это настоящая машина в облаке, а не строка в таблице. Фоновых действий нет совсем: ни авто-обновления с побочными эффектами, ни «починить за вас». Приложение читает по запросу и меняет по кнопке.

Звучит как очевидность, но соблазн сделать «умнее» возникает постоянно, и каждый раз его надо давить.

## Как всё это тестировать без облака

Тут и выстреливает разделение «вызов CLI отдельно, парсер отдельно». Парсеры — чистые функции, в них подаётся настоящий JSON (из моего каталога, с заменёнными на документационные адресами и именами), и они проверяются обычными юнит-тестами. Без сети, без аккаунта, на любой машине, в том числе в CI.

Интерфейс проверяется поверх фейкового бэкенда: Playwright поднимает фронтенд, а вместо Tauri-команд подставляются заготовленные ответы. Получается тест, который читается как сценарий:

```ts
test("a CLI without billing commands is explained, with a link to the console", async ({ app, page }) => {
  await app.override("yc_billing", { supported: false, accounts: [] });
  await page.locator('.yc-tabs [data-t="bill"]').click();
  await expect(page.locator(".yc-body")).toContainText("не умеет показывать платёжные аккаунты");
  await expect(page.locator(".yc-body")).not.toContainText("Unknown command");
  await page.locator("[data-a=billing-web]").click();
  expect((await app.called("open_external")).args).toEqual({ url: "https://console.yandex.cloud/billing" });
});
```

Отдельный сценарий — «CLI не установлена вообще»: раздел обязан объяснить, что поставить, показать кнопку «указать путь» и при этом **не сходить в облако ни разу**:

```ts
expect(await app.calls("yc_clouds")).toHaveLength(0);
expect(await app.calls("yc_instances")).toHaveLength(0);
```

Такие тесты ловят не опечатки, а регрессии в поведении — то есть ровно то, за что пользователь перестаёт доверять приложению.

## Что ещё приехало в 0.8.0

Чтобы статья не была только про облако, коротко об остальном релизе.

**Файлы на хостах.** Двухпанельный файловый менеджер: слева своя машина, справа хост, перетаскивание мышью между панелями, колонка с датой, сортировка по колонкам, папки всегда сверху, а перенесённый файл выделяется в панели-приёмнике, чтобы было видно, что именно приехало. Копирование с хоста на хост — через `scp -3`, оба соединения ведёт приложение.

**Kubernetes.** Теперь видно, что связь с кластером оборвалась: таблица гаснет и подписывается «данные на 14:32:05». До этого была отличная ловушка — правишь ConfigMap, перечитываешь, видишь старое значение и думаешь, что правка откатилась. Ещё добавились плашки namespace отдельной строкой, график над логами и честный отчёт о том, что реально применилось.

**Локальная ИИ.** Модели весят гигабайты, и качались они долго и обидно: оборвалась сеть — начинай сначала. Сделал загрузку в четыре потока по Range-запросам и докачку с места обрыва, с сохранением состояния частей на диск.

**И настройки, которые перестали пропадать.** Был отчёт: «после обновления пришлось заново указывать путь к Obsidian». Причина — обычная запись конфига поверх существующего файла. Теперь запись атомарная: временный файл, `sync_all`, переименование, а предыдущая версия остаётся как `.bak`, из которой читаем, если основной файл побился. Это тот случай, когда баг на три строки кода стоит пользователю получаса раздражения.

## Что дальше по облаку

Сейчас в разделе — машины, сети и подсети, группы безопасности, адреса, сервисные аккаунты с ролями и счёт. Дальше напрашиваются managed-базы (у меня уже есть раздел для баз, логично соединить), Object Storage рядом с файловым менеджером и метрики в разделе мониторинга.

Если вы из Yandex Cloud и читаете это: мне было бы полезно понять, как вы смотрите на такие внешние инструменты, и какие вещи в CLI вы считаете стабильным контрактом, а какие — нет. История с `billing` показала, что обёртка без этого знания ломается молча.
